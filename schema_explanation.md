# Database Schema Explanation: Accounts, Organizations & RBAC

This document provides a detailed, plain-language and technical explanation of the architecture, table responsibilities, and relational connections in [`accounts_orgs_schema.sql`](file:///c:/Users/Pablo/Documents/projects/learning-backend/accounts_orgs_schema.sql).

---

## 1. Core Architectural Concepts

The schema implements a modern, enterprise-grade **Multi-Tenant Software-as-a-Service (SaaS)** architecture using PostgreSQL 14+. It balances personal account ownership with organizational team structures through five key design principles:

1. **Single Global Identity (`users`)**: A single real-world person maintains exactly one user account regardless of how many organizations or workspaces they belong to.
2. **Decoupled Multi-Tenancy (`memberships`)**: Organizations (`organizations`) do not own user rows. Instead, `memberships` acts as a join table linking `users` to `organizations` with a specific role assignment.
3. **Hybrid Role-Based Access Control (RBAC)**: System-defined roles (`owner`, `admin`, `member`, `viewer`) operate alongside organization-scoped custom roles seamlessly using a unified permissions model (`roles`, `permissions`, `role_permissions`).
4. **State Independent Invitations (`invitations`)**: Pending team invitations exist independently of user accounts. A user does not need an existing system account to be invited to an organization.
5. **Polymorphic Ownership (`projects`)**: Resources can be owned either directly by an individual user (personal workspace) or by an organization (team workspace), enforced at the database level via PostgreSQL check constraints.

## 2. Comprehensive Table-by-Table Breakdown

The schema consists of **13 tables**, categorized into 5 logical modules:

---

### Module A: Identity & User Authentication

#### 1. `users`
- **Purpose**: Represents a single human entity (personal account). It serves as the primary root for authentication, personal resource ownership, and team memberships.
- **Key Columns**:
  - `id` (`uuid`): Primary key generated via `gen_random_uuid()`.
  - `email` (`citext`): Case-insensitive email address (ensures `User@Acme.com` and `user@acme.com` collide as the same identity).
  - `password_hash` (`text`): Stores hashed password (nullable to support SSO/OAuth-only users without passwords).
  - `email_verified_at` (`timestamptz`): Timestamp indicating when email ownership was confirmed.
  - `deleted_at` (`timestamptz`): Nullable timestamp supporting **soft deletion** (hides deactivated users without breaking historic records).

#### 2. `identities`
- **Purpose**: Stores external authentication links (OAuth, SAML, Google, GitHub) connected to a user account.
- **Key Columns**:
  - `user_id` (`uuid`): Foreign key referencing `users.id` (`ON DELETE CASCADE`).
  - `provider` (`text`): Identity provider type (e.g., `'github'`, `'google'`, `'saml:acme'`).
  - `provider_user_id` (`text`): Unique external identifier assigned by the OAuth provider.
- **Connections & Rationale**: One user can link multiple OAuth providers. The unique constraint `(provider, provider_user_id)` prevents duplicate accounts across external log-ins.

#### 3. `sessions`
- **Purpose**: Manages active stateful user sessions (e.g., web browser logins).
- **Key Columns**:
  - `token_hash` (`text`): Hashed session identifier to protect raw session tokens stored in client cookies.
  - `expires_at` / `revoked_at`: Controls session lifetime and instant session termination (sign out all devices).
  - `ip_address` / `user_agent`: Security metadata for fraud detection and session management UIs.

#### 4. `api_tokens`
- **Purpose**: Stores personal access tokens generated by users for programmatic API usage.
- **Key Columns**:
  - `token_hash` (`text`): Securely hashed API token.
  - `scopes` (`text[]`): PostgreSQL array of permissions (e.g., `{'project:read', 'project:write'}`) granted specifically to this token.
  - `last_used_at` (`timestamptz`): Auditing field to track token activity.

---

### Module B: Multi-Tenant Organizations & Auto-Onboarding

#### 5. `organizations`
- **Purpose**: The multi-tenant workspace boundary (e.g., a company, team, or project group).
- **Key Columns**:
  - `slug` (`citext`): Case-insensitive unique URL identifier (e.g., `app.com/orgs/acme-corp`).
  - `billing_plan` (`text`): Subscription tier (e.g., `'free'`, `'pro'`, `'enterprise'`).
  - `created_by` (`uuid`): Foreign key referencing `users.id` (`ON DELETE SET NULL`), recording who originally created the org.

#### 6. `trusted_domains`
- **Purpose**: Automated domain-based team onboarding. Allows organizations to auto-join employees with verified company email domains.
- **Key Columns**:
  - `organization_id` (`uuid`): The organization offering auto-join.
  - `domain` (`text`): Target email domain (e.g., `'acme.com'`).
  - `default_role_id` (`uuid`): Foreign key referencing `roles.id`, specifying the role assigned to matching new registrants.

---

### Module C: Role-Based Access Control (RBAC)

#### 7. `roles`
- **Purpose**: Defines sets of access levels assigned to users in an organization. Supports both global system defaults and per-org custom roles.
- **Key Columns**:
  - `organization_id` (`uuid`): Foreign key referencing `organizations.id`.
    - **If `NULL`**: Represents a global system role (`owner`, `admin`, `member`, `viewer`) shared across all organizations.
    - **If non-`NULL`**: Represents a custom role exclusive to that specific organization (e.g., `'billing_only'`).
  - `is_system` (`boolean`): Flags pre-seeded system roles.

#### 8. `permissions`
- **Purpose**: Catalogs granular operational privileges throughout the system.
- **Key Columns**:
  - `key` (`text`): Standardized permission string (e.g., `'org.manage_billing'`, `'project.create'`, `'project.delete'`).
  - `description` (`text`): Human-readable explanation.

#### 9. `role_permissions`
- **Purpose**: Many-to-many join table mapping `permissions` to `roles`.
- **Key Columns**:
  - `role_id` (`uuid`) & `permission_id` (`uuid`): Composite primary key.
- **Function**: Queries on this table determine if a role possesses a required capability (e.g., checking if the `'admin'` role has `'project.create'`).

---

### Module D: Organization Membership & Invitation Lifecycle

#### 10. `memberships`
- **Purpose**: The core join table connecting a `user` to an `organization`, conferring active membership with a specific `role`.
- **Key Columns**:
  - `user_id` & `organization_id`: Composite unique constraint `(user_id, organization_id)` ensuring a user holds only one active membership per organization.
  - `role_id` (`uuid`): Points to the assigned role (`roles.id`).
  - `status` (`text`): Restricts membership state (`'active'` or `'suspended'`).
  - `invited_by` (`uuid`): Points to the `user` who granted or initiated access.

#### 11. `invitations`
- **Purpose**: Represents pending membership offers sent to email addresses before or after user account creation.
- **Key Columns**:
  - `email` (`citext`): The target recipient email.
  - `token` (`text`): Secret random token included in invitation links.
  - `status` (`text`): Constrained state machine (`'pending'`, `'accepted'`, `'revoked'`, `'expired'`).
- **Lifecycle Logic**:
  1. An admin sends an invite -> row created in `invitations` with `status = 'pending'`.
  2. The recipient clicks the link -> System matches `token` and `email`.
  3. If accepted -> `invitations.status` switches to `'accepted'`, and a new row is written into `memberships`.

---

### Module E: Resource Ownership & Audit Trails

#### 12. `projects`
- **Purpose**: Sample resource entity illustrating **polymorphic ownership**.
- **Key Columns**:
  - `owner_user_id` (`uuid`): References `users.id` (Personal project).
  - `owner_organization_id` (`uuid`): References `organizations.id` (Team/Org project).
- **Polymorphic Constraint**: Enforced by `chk_projects_single_owner`:
  ```sql
  check (num_nonnulls(owner_user_id, owner_organization_id) = 1)
  ```
  This guarantees that every project is owned by **either** an individual user OR an organization, eliminating ownership ambiguity.

#### 13. `audit_logs`
- **Purpose**: Append-only security and compliance log tracking sensitive system actions.
- **Key Columns**:
  - `organization_id` (`uuid`): The organization context (null for personal actions).
  - `actor_user_id` (`uuid`): The user who initiated the action (`ON DELETE SET NULL` preserves historical audit records if user accounts are deleted).
  - `action` (`text`): Action identifier (e.g., `'membership.role_changed'`).
  - `metadata` (`jsonb`): Arbitrary contextual payload (IP addresses, previous/new values).

## 3. How the Tables Interconnect: Detailed Workflows

```
       [ identities ] ---------\
       [ sessions ] ----------+---> ( USER IDENTITY ) <---+--- [ audit_logs ]
       [ api_tokens ] ---------/         |                |
                                         |                |
  [ projects (Personal) ] <--------------+                |
                                         |                |
                                    [memberships] <-------+
                                         |                |
  [ projects (Org) ] <-------------------+                |
                                         |                |
       [ trusted_domains ] ----> ( ORGANIZATION ) --------+
       [ invitations ] ----------/       |
                                         |
                                     [ roles ] === [ role_permissions ] === [ permissions ]
```

### Workflow 1: User Login & Session Creation
1. A user authenticates via OAuth or password.
2. PostgreSQL verifies `users.email` and `password_hash`, OR matches `identities.provider_user_id` to retrieve `users.id`.
3. A row is added to `sessions` (web UI) or an `api_tokens` row is verified for API calls.

### Workflow 2: Organization Creation & RBAC Resolution
1. A user creates an organization -> inserted into `organizations` with `created_by = user.id`.
2. System attaches a `memberships` row linking `user_id` + `organization_id` with `role_id` pointing to system role `'owner'`.
3. When performing an action (e.g., deleting a project):
   - System looks up `memberships.role_id`.
   - Joins `role_permissions` -> `permissions` to check if `key = 'project.delete'` exists.

### Workflow 3: Inviting & Onboarding Members
1. **Direct Invite**: Admin creates `invitations` row. Accept link converts `invitations` to `memberships`.
2. **Domain Auto-Join**: User registers with `jane@acme.com`. System queries `trusted_domains` for domain `'acme.com'`, finds matching `organization_id` and `default_role_id`, and automatically writes a `memberships` row.

## 4. Key Database Constraints & Integrity Rules

| Feature / Technique | SQL Implementation | Benefit |
| :--- | :--- | :--- |
| **Case-Insensitive Text** | `citext` extension | Prevents email duplicate bugs (`User@Domain.com` vs `user@domain.com`). |
| **Polymorphic Constraint** | `num_nonnulls(...) = 1` | Prevents orphaned resources or dual-ownership bugs. |
| **Soft Delete** | `deleted_at timestamptz` | Allows un-deleting accounts/orgs while keeping analytics intact. |
| **Auto-Timestamp Triggers** | `set_updated_at()` trigger | Automatically updates `updated_at` on updates without application code logic. |
| **Cascade vs. Set Null** | `ON DELETE CASCADE` / `SET NULL` | Critical cascading deletions (deleting user removes sessions; deleting org sets audit actor/creator to null). |
